# Prompt Runtime Governance

## Purpose
Treat prompts as governed infrastructure instead of scattered strings.

## Prompt runtime components
- templates
- fragments
- compiler
- policy inputs
- route/view/context injections

## Rules
- no raw prompt strings in UI components
- no raw prompt strings in route files
- no raw prompt strings in domain handlers unless explicitly generated by the prompt runtime
- prompts are compiled from governed inputs: mode, policy, structured controls, context keys, and approved business knowledge
- communication pacing should be compiled from governed ARCH communication window inputs rather than ad hoc verbosity instructions
- retrieval grounding should be compiled from governed grounding/transparency/persistence controls rather than ad hoc search instructions

## User control model
Users may edit:
- structured DISC controls
- structured ARCH controls
- structured grounding / transparency / persistence controls where appropriate
- approved guardrail fields
- other bounded behavior inputs

These structured controls should include communication windows where appropriate, as defined in `docs-governance/COMMUNICATION_WINDOWS.md`.

Users may not edit:
- compiled system prompt
- hidden policy directives
- execution-plane instructions
- raw base prompt templates directly

## Versioning
- templates and fragments are versioned assets
- prompt changes should be reviewed like code, not treated as casual text edits

## Build order for communication behavior
When compiling a governed voice agent:
1. role
2. emotion
3. DISC
4. ARCH communication windows
5. grounding and retrieval constraints
6. route/view/context constraints

This keeps business voice behavior concise and reduces drift toward long-form over-explaining.

## Machine-native communication controls
The runtime/compiler should prefer explicit machine-native constraints such as:

- token budgets
- percentage allocation by communication window
- turn-length limits
- handoff thresholds
- context expansion limits

over vague natural-language instructions like:

- "be concise"
- "don't explain too much"
- "send an SMS if needed"

## Retrieval behavior
The runtime should prefer explicit machine-native retrieval controls such as:

- grounding importance scales
- transparency scales
- persistence scales
- required/default/optional filters
- detailed-view hints

This allows the model to reason about retrieval quality, disclosure limits, and fallback behavior without vague natural-language coaching.

## Human-friction handling
When emotional friction is detected or expected:

- maintain enough Acknowledge and Reflect budget
- avoid collapsing too quickly into context or handoff
- let emotion, DISC, and ARCH work together instead of relying on a single tone instruction
