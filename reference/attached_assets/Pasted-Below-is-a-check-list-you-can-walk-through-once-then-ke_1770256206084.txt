Below is a “check-list” you can walk through once, then keep as a living doc.
It is split into two parts:

A. Things you still have to configure manually (numbers, services, credentials).
B. Things the new code is already doing for you (webhook auto-registration, status-callback capture, etc.).

If an item is already green on your side just tick it off; if it is red, do the step and re-deploy the “fix-all-webhooks” button the team added – that single call will push the new URLs to every number and messaging-service in the account.

A. MANUAL TWILIO-SIDE SETTINGS (one-time)
Twilio credentials in Replit
☐ ACCOUNT_SID = ACxxx… (store in Replit “Secrets”, not in code)
☐ AUTH_TOKEN = abcd…
☐ API_KEY / API_SECRET (optional – if you use key instead of token)

Messaging Service (if you want a single “pool” of numbers)
☐ Create a Service in Console → Messaging → Services → “Customer Care”
☐ Copy the MessagingServiceSid (MGxxx…) – give it to the bot builder if they want to pass it explicitly.
☐ Add every Twilio phone number you buy to that Service (the new code will do it automatically, but you can do it once now).

Phone numbers
☐ Buy at least one SMS-capable number in the same geo as your users.
☐ Enable “Transactional” or “Mixed” use-case in Console → Phone Numbers → [number] → Messaging → “Configure with…”
☐ Set Webhook URL to:
https://your-replit-app.id.repl.co/webhook/sms/incoming
(the new code will overwrite it anyway, but this stops the “blank webhook” warning).

Status-callback endpoint (already coded)
☐ Nothing to do – the new /webhook/sms/status route exists.
☐ Just verify it is publicly reachable:
curl -X POST https://your-replit-app.id.repl.co/webhook/sms/status
-d "SmsStatus=delivered"
→ should return 200.

Geolocation & sticky sender (optional)
☐ If you want the same user to always get the same number, turn ON
“Sticky Sender” and “Geomatch” in the Messaging Service settings.

10-DLC / A2P registration (US numbers only)
☐ If you send >3 k msgs/day to US handsets, create a 10-DLC campaign and link the Messaging Service to it.
☐ Otherwise you will hit 30003/30005 errors.

B. WHAT THE NEW CODE ALREADY DOES FOR YOU
Auto-detects the Replit domain
Every time you remix or the repl restarts the code calls
GET /fix-all-webhooks
and rewrites:

PhoneNumber → VoiceUrl = null  
PhoneNumber → SmsUrl = https://$REPL_ID.id.repl.co/webhook/sms/incoming  
PhoneNumber → SmsFallbackUrl = same  
PhoneNumber → SmsStatusCallback = https://$REPL_ID.id.repl.co/webhook/sms/status  

MessagingService → InboundRequestUrl = same SmsUrl  
MessagingService → StatusCallback = same status endpoint
Adds every new number to the “Customer Care” Messaging Service
(unless you explicitly pass ?messagingServiceSid=MGxxx in the POST).

Logs every status update
delivered, failed, undelivered, with Twilio error code (30001-30008)
so you can query your own /logs endpoint or watch Replit console.

UI health card
Collapsible “Webhook Settings” card shows:
- current public URL
- HTTP 200/4xx/5xx health
- “Fix all webhooks” button (calls the same endpoint as above).
All elements have data-testid for your e2e tests.

C. QUICK TEST SEQUENCE
Open your repl → Secrets → add ACCOUNT_SID and AUTH_TOKEN → restart.
In Twilio console buy one number → note the digits.
In repl browser open:
https://$REPL_ID.id.repl.co/fix-all-webhooks
→ you should see JSON: {“ok”:true, “numbersUpdated”:1, “servicesUpdated”:1}
Send an SMS from your handset to that Twilio number.
Watch Replit console – you should see:
POST /webhook/sms/incoming 200
and a second later
POST /webhook/sms/status delivered 200
Let your AI agent reply; you should receive the message on your handset.
In Console → Messaging → Logs you will also see the status callback row.
D. COMMON ERROR CODES YOU WILL NOW CATCH
30001 – Queue overflow (you hit rate limit)
30002 – Account suspended
30003 – Unreachable carrier (handset off)
30004 – Barred by carrier (spam)
30005 – Unknown destination (number de-activated)
30006 – Landline or unreachable
30007 – Carrier violation (content blocked)
30008 – Unknown error

The new /webhook/sms/status route writes these into your own DB/log – expose them in an internal dashboard so your ops team can retry or switch channel (email, push) when SMS fails.
